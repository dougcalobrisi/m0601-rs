## The mental model

Three facts explain almost everything about how this driver behaves:

1. **It's a polling protocol.** A drive command does not latch. The motor moves
   only while drive frames keep arriving (~50 Hz; up to 500 Hz). The CLI's
   `control`/`drive` run that loop for you; the library's `drive_*` methods send
   **one frame each** and your loop provides the cadence.

2. **Zero is not universally "stop".** A zero setpoint stops the wheel only in
   velocity mode. In position mode it commands a move to 0°; in current mode it
   commands zero torque (a coast). `safe_stop` exists precisely because of
   this — it forces velocity mode first.

3. **Telemetry comes in two layouts.** A `0x74` query reply carries winding
   temperature and a coarse 8-bit angle; a reply to a drive frame carries a fine
   16-bit angle and no temperature. The driver decodes each reply by the command
   that elicited it. See [Telemetry]({{< relref "library/telemetry" >}}).

## Requirements

- **Rust 1.88+** (edition 2024 plus let-chains).
- **Linux** is the tested platform. The serial layer is portable, but the
  `/dev/ttyUSB0` paths and the `dialout` group are Linux-specific.
- **18 V DC** motor power and a USB–RS485 adapter (DFRobot recommends the
  RainbowLink TEL0185).
